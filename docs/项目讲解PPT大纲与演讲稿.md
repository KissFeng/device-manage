### 第2页：项目背景与需求分析（1分钟）

#### 一、项目背景

传媒类院校设备管理面临的三大难题：

1. **设备种类繁多**
   - 相机、镜头、灯光、音频设备等
   - 每种设备有多个型号和个体
   - 管理复杂度高

2. **传统流程效率低**
   - 纸质登记流程繁琐
   - 信息查询不便
   - 易出现登记错误

3. **设备状态难追踪**
   - 设备位置不明确
   - 借用状态难查询
   - 易出现丢失或损坏

#### 二、项目目标

构建数字化设备管理平台，实现：
- ✅ 设备信息集中管理
- ✅ 借用申请在线提交
- ✅ 审批流程自动化
- ✅ 设备状态实时追踪
- ✅ 借用记录完整归档

**实现效果**：
```

  ├─ 实例2：佳能 EOS R5-002（借用中，已借出）
  └─ 实例3：佳能 EOS R5-003（维修中，维修室）
```

---

#### 难点二：并发借用冲突

**问题描述**：
- 多个用户同时申请同一设备
- 可能出现超借问题
- 设备实例状态不一致

**解决方案**：
```java
@Transactional(rollbackFor = Exception.class)
public BorrowRecord applyBorrow(Long userId, BorrowRecord record) {
    // 1. 查询可用设备实例
    List<DeviceInstance> instances = deviceInstanceMapper
        .selectWithBorrowStatus(record.getDeviceId());
    
    // 2. 筛选正常且未借用的实例
    DeviceInstance availableInstance = instances.stream()
        .filter(inst -> "NORMAL".equals(inst.getStatus()))
        .filter(inst -> !isBorrowed(inst.getId()))
        .findFirst()
        .orElseThrow(() -> new BusinessException("暂无可用实例"));
    
    // 3. 分配实例并创建借用记录
    record.setDeviceInstanceId(availableInstance.getId());
    borrowRecordMapper.insert(record);
    
    return record;
}
```

**关键技术**：
- 数据库事务保证原子性
- 实时查询设备实例借用状态
- 乐观锁机制防止超借

### 【项目背景与需求分析】（1分钟）

首先，让我们看一下项目背景。

在传媒类院校中，设备管理一直是个难题。我们面临三大挑战：

**第一，设备种类繁多**。学校拥有各类专业设备，包括相机、镜头、灯光、音频设备等，每种设备又有多个型号和个体，管理起来非常复杂。

**第二，传统流程效率低下**。以往都是通过纸质登记的方式管理借用，流程繁琐，信息查询不便，而且容易出现登记错误或遗漏。

**第三，设备状态难以追踪**。管理员不清楚设备的实时位置和借用状态，容易导致设备丢失或损坏，责任也难以追溯。

因此，我们的目标是构建一个数字化的设备管理平台，实现从借用申请、审批到归还的全流程在线管理，让设备管理更高效、更安全、更透明。

### 【系统架构设计】（1.5分钟）

接下来介绍系统架构。我们采用了前后端分离的三层架构设计。

**在技术选型方面**：

前端使用HTML5、CSS3和原生JavaScript开发，没有引入复杂的框架，保证了系统的轻量级和高性能。同时采用响应式设计，可以适配电脑、平板和手机等多种设备。

### 【数据库设计】（1.5分钟）

数据库设计是系统的核心基础。我们设计了5张核心数据表：

**第一，用户表（users）**：管理系统用户，支持三级权限体系——ROOT超级管理员、ADMIN管理员和USER普通用户。ROOT拥有最高权限，可以管理所有用户和设备；ADMIN可以管理设备和审批借用，但只能管理普通用户；USER只能浏览设备和申请借用。

**第二，分类表（categories）**：对设备进行分类管理，比如相机、镜头、灯光、音频设备等，方便用户快速查找。

**第三和第四，设备表（devices）和设备实例表（device_instances）**：这是我们数据库设计的亮点。我们采用了"设备模板+设备实例"的两层结构。

设备表存储设备的基本信息，比如"佳能EOS R5"，这是一个模板；设备实例表存储具体的设备个体，比如"佳能EOS R5-001"、"佳能EOS R5-002"、"佳能EOS R5-003"，每个实例都有独立的状态、位置和描述。

这样设计的好处是：可以灵活管理同型号的多个设备，每个设备实例的状态独立追踪。比如，001号机正常可借，002号机正在被借用，003号机正在维修，互不影响。

**第五，借用记录表（borrow_records）**：记录借用的全流程信息。我们设计了完整的状态机：从PENDING（待审批）到APPROVED（已批准）再到RETURNED（已归还），或者直接到REJECTED（已拒绝）。每条记录都包含申请人、审批人、设备实例、时间节点等完整信息。

所有表之间通过外键建立关联，比如删除设备前会检查是否有借用记录，删除用户前会检查是否有未归还设备，保证了数据的一致性和完整性。

### 【核心功能演示——用户端】（1.5分钟）

现在演示核心功能。首先是用户端功能：

**第三个功能是我的借用记录**。用户可以查看自己的所有借用记录，包括待审批、已批准、已拒绝和已归还的记录。每条记录都显示了设备信息、借用时间、审批状态等。用户还可以按状态筛选，比如只看"待审批"的申请。

整个用户端的设计理念是简洁、直观、易用，让用户能够快速完成借用申请。

### 【技术实现亮点】（1.5分钟）

在技术实现方面，我们有几个值得介绍的亮点：

**第一，安全性设计**。

我们使用JWT Token实现无状态认证。用户登录成功后，后端生成一个JWT Token返回给前端，Token中包含了用户ID、用户名和角色信息。前端将Token存储在localStorage中，后续的每个请求都在请求头中携带这个Token。后端通过JWT过滤器验证Token的有效性，解析出用户信息，并检查权限。Token有效期是24小时，过期后需要重新登录。

密码采用BCrypt加密存储。BCrypt是一种单向加密算法，加密后的密码无法解密，而且每次加密的结果都不同，即使数据库泄露，黑客也无法破解原始密码。

我们还实现了基于角色的权限控制。在Controller层，使用注解标记需要的权限，Spring Security会自动检查当前用户是否有权限访问。比如，删除用户的接口只有ADMIN和ROOT可以访问，普通用户访问会返回403权限不足。

**第二，用户体验优化**。

我们使用了CSS3的backdrop-filter属性实现毛玻璃效果。所有的卡片、模态框、导航栏都有半透明背景加上模糊效果，视觉层次分明，界面非常现代化。

响应式设计方面，我们使用了CSS Grid和Flexbox布局，配合媒体查询，可以自动适配不同屏幕尺寸。在电脑上是多列网格布局，在手机上自动切换为单列布局。

前端采用异步加载技术，所有的数据请求都是异步的，用户操作后会显示加载状态，数据加载完成后自动刷新页面，整个过程非常流畅，无需手动刷新。

**第三，代码质量保障**。

后端统一使用Result类封装所有接口的响应，包含code状态码、message消息和data数据三个字段。这样前端可以统一处理响应，代码更规范。

我们实现了全局异常处理器，捕获所有的异常，包括业务异常、参数校验异常、认证异常等，统一转换为JSON格式返回给前端，避免了敏感信息泄露，也让用户看到友好的错误提示。

在涉及多个数据库操作的业务方法上，我们都添加了@Transactional注解，使用Spring的事务管理。比如批准借用时，需要更新借用记录状态、检查设备实例状态，这些操作要么全部成功，要么全部回滚，保证了数据的一致性。

### 【项目难点与解决方案】（1分钟）

在开发过程中，我们遇到了几个技术难点，在这里分享一下我们的解决方案：

**难点一：设备实例管理**。

最初我们只设计了设备表，但很快发现无法管理同型号的多个设备。比如学校有3台佳能EOS R5，如果只有一条设备记录，就无法追踪每台相机的具体状态和位置。

我们的解决方案是引入了设备实例表，将设备分为"模板"和"实例"两层。设备表存储设备的通用信息，作为模板；设备实例表存储每个具体的设备个体，每个实例都有独立的状态、位置和描述。借用时，系统会自动分配一个可用的实例，归还时释放该实例。这样既保证了灵活性，又实现了精细化管理。

**难点二：并发借用冲突**。

多个用户同时申请同一设备时，可能出现超借问题。比如，设备只有1个可用实例，但2个用户几乎同时提交申请，如果不加控制，可能都会成功，导致冲突。

我们通过数据库事务和实时状态检查解决了这个问题。在借用申请的Service方法上添加了@Transactional注解，整个操作是原子性的。系统会先查询所有可用的设备实例，筛选出状态为"正常"且未被借用的实例，如果找不到可用实例，直接抛出异常"暂无可用实例"。这样就避免了并发冲突。

**难点三：跨域请求问题**。

前后端分离部署时，前端运行在一个端口（比如9012），后端运行在另一个端口（比如9011），浏览器会拦截这种跨域请求，导致前端无法调用后端API。

我们在Spring Security配置中添加了CORS配置，允许所有来源的跨域请求，支持GET、POST、PUT、DELETE等所有HTTP方法，并设置了预检请求的缓存时间为1小时。这样就完美解决了跨域问题，前后端可以正常通信。

### 2. 设备实例自动分配
```java
@Transactional(rollbackFor = Exception.class)
public BorrowRecord applyBorrow(Long userId, BorrowRecord record) {
    // 查询可用的设备实例
    List<DeviceInstance> instances = deviceInstanceMapper
        .selectWithBorrowStatus(record.getDeviceId());
    
    DeviceInstance availableInstance = null;
    for (DeviceInstance instance : instances) {
        // 检查实例状态是否为正常
        if (!DeviceStatus.NORMAL.getCode().equals(instance.getStatus())) {
            continue;
        }
        
        // 检查实例是否已被借用
        LambdaQueryWrapper<BorrowRecord> borrowWrapper = new LambdaQueryWrapper<>();
        borrowWrapper.eq(BorrowRecord::getDeviceInstanceId, instance.getId())
                .in(BorrowRecord::getStatus, 
                    BorrowStatus.PENDING.getCode(), 
                    BorrowStatus.APPROVED.getCode());
        Long borrowCount = borrowRecordMapper.selectCount(borrowWrapper);
        
        if (borrowCount == 0) {
            availableInstance = instance;
            break;
        }
    }
    
    if (availableInstance == null) {
        throw new BusinessException("该设备暂无可用实例");
    }
    
    record.setDeviceInstanceId(availableInstance.getId());
    record.setUserId(userId);
    record.setStatus(BorrowStatus.PENDING.getCode());
    borrowRecordMapper.insert(record);
    
    return record;
}
```
